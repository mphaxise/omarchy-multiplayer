# Session note: Phase 1 baseline

- Date: 2026-09-02, 11:28 to 11:33 PDT guest time
- Provenance: hands-on, driven over ssh from the Mac; screenshots by `grim`, window state by `hyprctl clients -j`, process state by `pgrep`
- Environment: aarch64 UTM VM (unofficial ggalancs image), Herdr 0.8.2, Claude Code 2.1.252 via mise shim, Alacritty as the agent terminal, software rendering
- Deviation from the plan: captured on the `dev-2026-09-01` disk, which already carried sshd, a Herdr server, the Claude login, and a throwaway repo. None of those touch the surfaces captured. Praneet approved the rerun on this disk.
- Caveat: unofficial-port. Terminal windows render no text in screenshots on this rig (both the keybinding agents and the Herdr client came out as transparent frames), so terminal content is evidenced by `herdr pane read`, window titles, and process lists, and screenshots carry only window geometry, dialogs, and notifications.

## Scenario A, two agents from the keybinding path

`omarchy-agent-prompt` twice. Each launch opened an Alacritty window with class `org.omarchy.agent`; the window title mirrors Claude Code's own state ("✳ Awaiting instructions", "✳ Ready signal"), which is the only place the two windows differ. Both runs were `claude --permission-mode auto -- <prompt>`. Every launch raised a `gcr-prompter` modal, "Authentication required: an application wants access to the keyring 'Default Keyring', but it is locked", with no Omarchy framing (`baseline-a2-…`). Ending the first terminal ended its Claude process within three seconds; the second kept running (`baseline-a3-…`): a run lives exactly as long as its terminal. A third launch from the same path started a fresh conversation with no offer to resume the one that ended. Nothing in the bar or the shell lists the runs; the usage widget is the only agent surface in the bar.

## Scenario B, Herdr

`omarchy-launch-terminal-herdr` opened an Alacritty window titled `omarchy: spike` attached to the persistent session. A Claude Code pane started through the API went `idle`, then `working` and `done` across one turn, visible in `herdr agent list`. Closing every Herdr client window left the agent tracked and its transcript intact (`herdr pane read` still showed the prompt), and a new client showed it again (`baseline-b3-…`). Two Herdr client windows open at once mirror the same session. Claude in a Herdr pane raised the same keyring modal.

## Scenario C, the crash path

`sh -c 'kill -SEGV $$'` produced a coredump; within four seconds the top-right notification read "Process crashed: bash / Click to diagnose with AI" (`baseline-c1-…`). Invoking the click target (`omarchy-agent-crash <pid>`) opened an `org.omarchy.agent` window with Claude Code and the diagnosis prompt (`baseline-c2-…`), which then raised the keyring modal too.

## What this establishes for the experiment

The three success-signal gaps are confirmed on the rig: no list of running agent work, a run bound to its terminal's lifetime, and no record after a run ends. Herdr already supplies the durable process and the status; it does not supply identity, lineage, or a receipt, and its client windows carry no per-agent state into the shell.
