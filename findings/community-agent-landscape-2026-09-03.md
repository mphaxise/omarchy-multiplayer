# Who else is doing persistent agents, agent teams, or org-level Omarchy

Status: research note, 2026-09-03, afternoon; the three threads at the end were pulled further the same evening (Maestro's source, Axon's docs, and every comment on #7956, each read by a subagent that cites what it opened). Sources: the Omacom Discord (server search, read through the web app: swarm, "multiple agents", orchestration, persistent, "persistent agent", openclaw, fleet, enterprise, "multiple users", worktree, ralph), GitHub Discussions and Issues on `omacom/omarchy`, the marketplace repository, `plugins.omarchy.org`, `omarchyplugins.com`, and web search. The GitHub half was gathered by a subagent that opened each page it cites; items marked *snippet* come from a search result it did not open. Nothing was posted or replied to during the sweep.

## The result

Nobody in the Omarchy community is building a durable session object with receipts, and nobody is coordinating a team of agents on one goal from the desktop. The nearest things are resume tools (Session Browser, Hermes Sessions), monitors (Agent Orchestrator, the Herdr bar plugin), and worktree-per-agent launchers (Maestro, `tsl`, agentic-dev-setup, qj-orch, `preview`). The demand is there in the chat: people ask how to run an agent somewhere it survives and cannot hurt them, how to run several at once without losing track, and how to give an agent its own user. Org-level Omarchy exists on two fronts that have nothing to do with agents yet: upstream's unattended installs and Fleet's MDM support, plus one home fleet with agents as participants. Multi-user is the standing gap upstream has promised for 4.1.

## Three threads, pulled further

### Maestro against lanes

Maestro is a Rust terminal app (ratatui, portable-pty, tui-term), version 0.1.0, MIT, ten commits all on 2026-08-19, 7 stars, no release, no AUR package, issues disabled ([repo](https://github.com/ivancernja/maestro), [README](https://raw.githubusercontent.com/ivancernja/maestro/main/README.md)). On Omarchy it reads the theme, uses `omarchy-notification-send`, and defaults to `omarchy default agent`. It launches nine harnesses with the same auto-approve flags `bin/omarchy-agent` uses (`claude --permission-mode auto`, `codex --approve-for-me`, `gemini --yolo`), copied from that script ([agent.rs](https://raw.githubusercontent.com/ivancernja/maestro/main/src/agent.rs)). `n` opens a four-step form (repo, branch, agent, optional task); a workspace is one worktree on a new branch in Omarchy's `ga` layout, one detached tmux session named `mst-<repo>--<branch>`, and the task passed once as the prompt flag ([app.rs](https://raw.githubusercontent.com/ivancernja/maestro/main/src/app.rs), [git.rs](https://raw.githubusercontent.com/ivancernja/maestro/main/src/git.rs)). State is a hash of `tmux capture-pane` every 1.2 s: unchanged for 3 s means quiet; the README says it cannot tell "waiting for approval" from "finished", and only a working-to-quiet flip on an unfocused workspace sends a toast ("<branch> is waiting"). Persistence is tmux with `remain-on-exit`: the agent survives quitting the app and closing the terminal; after a reboot a workspace shows `✗` and `R` restarts the bare CLI with no task and no resume. `L` runs `git merge --no-ff --no-edit` in the main checkout after four checks (clean worktree, branch ahead, main on base and clean) and then deletes the session, the worktree, the branch, and the record; a failed merge is red footer text with no abort in the source, so the main checkout is left mid-merge (inferred from the code). One JSON per workspace under `~/.local/state/maestro/ws/` with id, branch, repo, worktree, agent, base, session, and created time: no task, no transcript, no receipt, and the record is deleted on landing ([registry.rs](https://raw.githubusercontent.com/ivancernja/maestro/main/src/registry.rs)). No ssh, remote, or second person. It copies Conductor's worktree-per-task model, status sidebar, and merge-then-retire, and drops Conductor's PRs, checks, diff viewer, cloud sandboxes, multiplayer, and history ([conductor.build](https://www.conductor.build/), [workflow](https://www.conductor.build/docs/concepts/workflow)).

| Lane property | Maestro |
|---|---|
| One task per agent inside one shared session | Similar: one task per workspace, workspaces flat and independent, nothing groups them |
| Second agent from the bar panel with one key | Similar: `n` inside the TUI, four fields; nothing outside the app |
| Each lane on its own worktree cut from the session branch | Has it: `worktree add -b` from the main checkout's branch, base recorded |
| A blocked lane named on the toast and the row | Similar: "went quiet" gives a mark, a header count, one toast; it cannot say why, and exits do not notify |
| `done --lane` merges onto the session branch; a conflict is a blocked lane | Similar: `L` guarded merge then retire; a conflict is footer text with no state change and no abort |
| A receipt with commits per lane | Lacks; a live `+N −M` diffstat only, and the record dies on landing |
| Survives terminal close and reboot, with resume | Similar: survives quit and terminal close through tmux; after a reboot it is `✗` and restarts fresh (inferred) |

What lanes have that Maestro does not: the shared goal, the completion path to the parent, the conflict as a state with both trees intact, the receipt, and the reboot. What Maestro has that lanes do not: nine harnesses launched with their real flags, a status sidebar without Herdr, and `lazygit` on `g`. Its quiet-detection by screen hash is the failure Herdr's manifests avoid. A fair sentence for the slice-2 report: Maestro is Conductor's worktree-per-agent model brought to the terminal on Aug 19; Keepalive puts the same worktrees inside a session that keeps the goal, the outcome, and the record.

### Axon: beside the desktop, one machine, observed

Axon is a TypeScript-on-Bun agent framework and runtime by "Arc Labs" (GitHub org `artificial-cognition-laboratories`, a read-only mirror, 7 stars, no license file, last update Aug 29; the site's YouTube link is `@CodyWakeford`, and the Axon Discord's invite was created by a user shown as "Cody", 32 members) ([site](https://axon.arclabs.it/), [repo](https://github.com/artificial-cognition-laboratories/axon), [install](https://axon.arclabs.it/docs/v2/getting-started/installation)). An agent is a folder: a Vue component rendered to Markdown as the system prompt, tools, a config with policy and modules, API routes, and a `data/` directory that survives restarts and redeploys ("the session is ephemeral, the folder is not"); each agent gets a `did:key` identity on first boot ([agent dir](https://axon.arclabs.it/docs/v2/agent/agent-dir), [state](https://axon.arclabs.it/docs/v2/concepts/state-model)). It runs as a local HTTP server with a TUI, as a one-shot headless command, or as a container; deploy is Axon Cloud (durable data, scale to zero, cron) or `docker run`; a registry distributes agents and modules (82 artefacts from two publishers, most with zero installs) ([deploy](https://axon.arclabs.it/docs/v2/deploy), [registry](https://axon.arclabs.it/registry)). On Linux its policy becomes mount and network namespaces, nftables, and cgroups ([policy](https://axon.arclabs.it/docs/v2/agent/policy)). Models: providers declared once per profile, a role-matched runtime choice at boot, routes through its managed service, Codex, OpenRouter, eleven vendors, and Ollama, whose server and downloads the terminal manages ([providers](https://axon.arclabs.it/docs/v2/providers)).

"Fleet" today means one machine, observed rather than owned: every booted agent registers itself on the machine, and the CLI, the terminal, and a VS Code extension called Axon Fleet (v0.2.18, seven installs) read the same registry, with Stop and open-in-TUI as the only controls; sessions are `.jsonl` files on disk and nothing is uploaded ([fleet](https://axon.arclabs.it/docs/v2/fleet/management), [drawers](https://axon.arclabs.it/docs/v2/fleet/drawers), [marketplace](https://marketplace.visualstudio.com/items?itemName=arclabs.axon-fleet)). A `Fleet({...})` call boots several agents in code and its docs page 404s. Cross-machine reach is `:attach <url>` to a deployed instance. No Omarchy or Arch page, plugin, or announcement exists, the marketplace's `registry.json` has no `axon`, and two registry agents look Linux-flavoured (`@axon/oma`, published hours before the check, no README) ([oma](https://axon.arclabs.it/@axon/oma)). Herdr's detection list does not include Axon.

For the plan: Axon sits beside Herdr as another runtime with its own TUI, and would run inside a Herdr pane undetected unless a manifest is added; nothing public keeps its instances alive across a logout except its cloud. "Native fleet manager" most plausibly means a Quickshell panel over its local instance registry and model palette, which is inferred, not announced. A session layer could interoperate by reading that registry, the session `.jsonl` titles, and its event stream (`capsule:escalating`, `thread:end`) for notifications and receipts; answering an escalation from the bar would need its undocumented TUI thread protocol. Watch it; do not plan around it.

### #7956: a VM is the identity, and the person disappears into it

The thread is ggalancs's, about his aarch64 UTM image builder; BeachFrontMT ("RBeach") posted five comments from Aug 31 to Sep 2 ([#18212136](https://github.com/omacom/omarchy/discussions/7956#discussioncomment-18212136), [#18238394](https://github.com/omacom/omarchy/discussions/7956#discussioncomment-18238394), [#18240027](https://github.com/omacom/omarchy/discussions/7956#discussioncomment-18240027), [#18251830](https://github.com/omacom/omarchy/discussions/7956#discussioncomment-18251830), [#18251954](https://github.com/omacom/omarchy/discussions/7956#discussioncomment-18251954)). The setup: an M1 Pro host, a UTM NAT guest among several house VMs; a hub ("KVM2") terminating OpenVPN with tls-crypt and ssh tunnels; a self-hosted RustDesk relay; an "ops hub" running Hermes Desktop remote-attached. Identity is "per-guest OpenVPN identity, pinned seat": an EasyRSA client profile with a fixed address, 10.80.0.6, which the VM "pulled its own OpenVPN profile" for over existing ssh trust. "Keyless" means no API keys on the guest: the model (GLM-5.3-flash through Ollama cloud) rides outbound ssh tunnels to the hub. Harnesses: opencode 1.18.25 and Hermes Agent 0.20.6; "ZippoAI" is Hermes on GLM. Two comments open "Reported on behalf of RBeach" and close as executed "from inside the VM's own VPN seat"; the marking is body text under the same GitHub account, and a later comment signs as the person: "the person holding the keyboard: it was me." What he asked upstream for: no zsh, an SDDM theme with no user picker, RustDesk transparent on Wayland, a VirtFS uid trap, Hyprland emergency mode after power-off, a guard for a config file the image rewrites; ggalancs replied on Sep 2 and promised a login-time check; no Omarchy maintainer replied. Persistence: the VPN seat survives the host leaving the LAN ("mobile continuity"), autologin at service start, a chown that "survives reboots". Receipts: none purpose-built; the forensics read both harness session stores, shell history, ssh logins, the journal, and the clipboard. One person and one agent share one VM and one session; no second person, no sharing.

Against slice 3's model (`human:<user>@<host>`, a second person from another host, a blocked agent answered at its keyboard or through an attach, presence per host): the per-VM seat gives the `<host>` half a name that survives the machine changing networks, a transport for a second person (VPN, ssh, RustDesk), attaches that cannot leak keys because the VM holds none, and an agent acting under its own seat, the shape of `agent:<name>@<host>`. It takes away the `<user>` half: person and agent arrive as the same address, which is why forensics were needed to learn who held the keyboard; agent authorship is prose under a human's account; presence per host becomes presence per VM; there is no blocked-agent path and no receipt beyond the harness stores; autologin as one admin user with no user picker makes the VM single-person by construction. The lesson for slice 3: keep the person and the agent as two actors on the record even when they share a seat, and treat the VM seat as the host, never as the identity.

## What this means for the plan

Judgment, not measurement. Keepalive's record and receipt have no neighbour; that is the thing to keep saying plainly. Lanes have one close neighbour, Maestro, and several homegrown versions (qj-orch, grbrum's planner and executors, agentic-dev-setup); none of them has the shared goal, the completion path, the conflict kept as a state, or the receipt per lane, and Maestro's record dies the moment a workspace lands, so slice 2's report compares against Maestro by name with the table above. The remote case is live now: Herdr on a VPS, Omarchy in QEMU as an agent workstation, a VPN seat per VM in #7956; slice 3's second-host path (an answer path for a blocked agent from another machine, Herdr `--remote`) is the next thing people would use, ahead of the second OS account, which waits on 4.1, and #7956 says what that path must keep: two actors on the record even on one seat. Axon is a runtime beside Herdr with a one-machine registry, not a control plane above the desktop; slice 4 can define fan-out without it, and a manifest for Herdr plus a reader for its registry would be the whole integration if it ever ships on Omarchy. And the recurring "run it somewhere safe" question suggests a section in the listing README on running Keepalive inside an Omarchy VM, since that is the sandbox DHH points people to.

## What this cannot claim

Discord's search is by keyword and returns the newest matches first; a conversation that used other words was missed, and long threads were read only where a hit led into them. GitHub's search pages could not be fetched, so the Discussions and Issues coverage came from web search plus opened pages; a discussion that search engines have not indexed was missed. `plugins.omarchy.org` is rendered by JavaScript and its catalogue was cut at 80k characters, so the plugin list is what OmaPicks, the marketplace issues, and opened repositories showed. Install counts are OmaPicks figures. Nothing here was verified by running the other tools: Maestro was read, not run; Axon's fleet claims come from its docs, with its GitHub API, blog, pricing page, and the `Fleet` docs page unreadable; Maestro's engagement on the showcase forum was not measured.
